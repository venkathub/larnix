01 / ONE REFUND, TWO RECORDS

A missing receipt
is a question.

BEFORE YOU BEGIN

The curriculum prerequisite is M21-L01: persist decision state. Know that an agent can call a tool and save a checkpoint. We recap both ideas here. No model, payment account or API key is required.

Outcome: explain the crash window and design recovery around a stable operation identity and evidence of completion. Allow 3–5 additional hours for the production exercise.

Our fictional camera-rental shop is returning a ₹500 deposit for rental R-104. A staff member has already authorized this exact refund. The assistant’s remaining job sounds simple: call the refund tool, save the receipt, tell the customer it is done.

The provider records the refund. Before the assistant saves the reply, its process crashes. On restart, the assistant reads its notebook: “Refund pending.” It submits the request again with a new reference number. Our deliberately permissive mock provider accepts it as another action. The customer now has two ₹500 refunds.

The arithmetic is easy: ₹500 + ₹500 = ₹1,000, when the authorized total was ₹500. The reasoning error happened earlier. The assistant treated “I did not record a result” as “the action did not happen.”

A notebook and a till

Imagine a shop colleague paying from a till and then ticking a box in a notebook. If they leave after paying but before ticking, an empty box cannot tell the next colleague whether the money left the till. There are two records to reconcile.

A checkpoint is a saved record the program can read after restarting. An external effect is a change outside that record: a refund, a sent email, a created ticket. The analogy helps locate the gap, but a computer also has temporary memory and messages that can be delayed, duplicated or lost. We must specify the behavior at those boundaries.

MAKE A PREDICTIONThe checkpoint says “pending” after a crash. What do we know about the refund?

    03 / FOLLOW THE RECEIPT

    Give the action an identity.
    Keep its evidence.

    Let’s repair the same story without pretending the crash window disappears. Before any call, save the exact intent: rental R-104, INR, ₹500, operation ID refund-R104-01, status pending, schema version 1. The operation ID identifies this one authorized business action. It is not a new number for every attempt.

    What idempotency buys us

    An idempotent operation has the same intended effect when repeated as when performed once. Our provider implements this with a key: the first call records the effect and a receipt together; a matching call with the same key returns that receipt. A different amount with the same key is rejected. A fresh key can create a fresh effect.

    This contract must be implemented where the effect happens. A flag in the agent’s memory cannot impose it on a remote service. In our mock, receipt lookup also returns the recorded outcome for an operation ID. This lookup is a teaching assumption, not a claim that every payment API exposes that endpoint.

    Notice what changed: recovery collected evidence instead of creating another action. Reconciliation means comparing the durable intent with the provider’s outcome and bringing local state into agreement. The checkpoint now holds the receipt associated with the original operation.

    If the crash happened before dispatch, the mock’s authoritative lookup finds no receipt. Recovery submits the same intent under the saved key and stores the reply. Even if the original request were delayed and arrived later, an atomic provider deduplication contract would need to keep both submissions from creating separate effects. This small lab does not simulate concurrent execution; your production exercise will test that assumption.

    A timeout leaves the original operation unresolved. Which identity should a retry use?

    You may give each attempt a separate trace ID while preserving the business operation ID.

    How does this connect to durable execution and replay? +

    Durable execution reconstructs progress from saved state or history. Temporal describes replay as checking generated commands against recorded history; LangGraph checkpointers persist graph state. Neither is modeled by our in-browser stepper: its “replay” button simply re-displays a precomputed fictional trace.

    For a real runtime, isolate effects behind activities or tools with explicit retry contracts. Reconstructing a decision is different from safely repeating the action it requested. Check the runtime’s own rules for persistence, replay and activity retries.

    04 / WHERE PROMISES BREAK

    Unknown is a state
    worth keeping.

    The reply arrived, but only in memory

    Choose “Receipt in memory” and replay from the start. The agent briefly has receipt-1; after the crash it does not. Durable state still says pending. The recovery requirement is the same as for a lost reply. Receiving a response is not the same as persisting it.

    The checkpoint already contains the receipt

    Choose “Checkpoint saved.” Recovery resumes the completed outcome without another tool call. This is useful evidence—but only because the record binds the receipt to the exact intent. A free-form note that says “looks done” is a weak substitute.

    The provider cannot answer right now

    Choose “Lookup unavailable.” You can see one effect in the observer panel, but the recovering agent cannot verify it. Our conservative policy holds the pending task and tries reconciliation later. It reports uncertainty instead of claiming success or failure.

    Some APIs permit a direct retry under a still-valid idempotency key even when a separate lookup is unavailable. That can be a valid policy under their documented contract. Our lab chooses to wait; it does not teach that holding is the only possible recovery design.

    Under this lab’s policy, receipt lookup times out. What happens next?

    A transport failure and an authoritative absence are different results.

    The assistant changes its mind on retry

    Choose “Changed amount.” Recovery tries ₹700 against a saved ₹500 intent and stops before submission. Bind authorization, operation identity and parameters together. If an amount genuinely needs changing, resolve the first operation and handle the new intent under the relevant approval policy. Never silently change a pending action because a regenerated model answer differs.

    Why not promise “exactly once”? +

    In the successful mock runs, one business effect is recorded. That conclusion depends on the stated provider contract and durable intent. It is not a universal delivery guarantee. A real request may be attempted more than once, and a remote service might not support deduplication at all.

    Key retention matters. For example, Stripe’s API v1 documentation allows old keys to be pruned after at least 24 hours; reuse after pruning is treated as a new request. Our mock never expires keys. A production recovery process must respect its provider’s retention window and resolve older uncertainty using durable business records or human review.

    What if we deploy new code while a task is pending? +

    Keep a schema version with saved state and test old pending records against the new reader. A migration must preserve the operation ID, parameters and receipt binding. If the new code cannot interpret an old intent, stop and reconcile it; do not regenerate a replacement identity. Runtime replay can impose additional code-versioning constraints beyond migrating a JSON checkpoint.

    06 / EXPLAIN IT BACK

    Describe the gap
    before the framework.

    INTERVIEW PROMPT

    “Why does checkpointing alone not guarantee exactly-once external effects?”

    A strong answer walks through one crash: the provider commits, the agent dies before saving the receipt, and pending local state survives. A blind retry can repeat the effect. Then explain your recovery contract: durable intent, stable identity, provider-side atomic deduplication, receipt reconciliation and an explicit unknown state.

    Expect follow-ups: What happens after key expiry? How do two workers race? Does a timeout mean rejection? Can a changed payload reuse the key? What happens to an old checkpoint after a deployment? Say which guarantees belong to the runtime, your application and the provider.

    A concise model answer +

    “A local checkpoint and a remote effect are separate writes. The process can fail after the remote write and before the local receipt is durable. I persist the authorized intent first, reuse its operation key and reconcile provider receipts before claiming completion. One-effect behavior depends on the provider’s atomic deduplication and retention contract. If I cannot determine the outcome, I keep it unresolved and apply a defined recovery policy.”

    07 / KEEP THE KEY IDEAS

    A restart should recover
    the original intention.

    1. A pending checkpoint is not proof that an external action failed.
    2. Saving intent before dispatch gives recovery an identity and parameters to preserve.
    3. Deduplication is a provider contract, not a property of a client-side label.
    4. Receipts connect completion evidence to the exact operation.
    5. Unknown outcomes, retention limits and old schemas need explicit policies.

    A small glossary

    Durable state
    Information that survives the failures covered by the storage system’s guarantees.
    Checkpoint
    A saved snapshot used to resume program progress.
    External effect
    A change outside the agent’s local execution state.
    Idempotency key
    An operation identifier a provider can use to recognize repeated requests under its contract.
    Receipt
    Recorded evidence identifying the provider’s outcome for an operation.
    Reconciliation
    Resolving differences between intended action, locally saved progress and external outcome.
