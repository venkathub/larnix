## M08-L01 — Design pretraining inputs

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M06-L04](M06.md#m06-l04), [M07-L04](M07.md#m07-l04)

**Learning outcome:** Describe how corpus choices influence downstream model behavior.

**Topics:** corpus mixtures; deduplication; contamination; token budgets; sequence packing.

**Study estimate:** 2–3 hours guided study + 3–5 hours exercise. These are uncalibrated learner-effort estimates, not measured timings or an implementation schedule.

### Primary readings

- [LLM: Hugging Face LLM course](https://huggingface.co/learn/llm-course/en/chapter1/1) — Transformer architectures, tokenizers, fine-tuning, NLP, limitations.
- [DATA: Hugging Face Datasets](https://huggingface.co/docs/datasets/index) — Loading, mapping, streaming, dataset processing.

### Interview question

Why can more training tokens reduce useful model quality?

**A strong answer addresses:** Data quality; mixture shift; duplicated signal.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Create a pretraining data card for a toy domain corpus with a fixed token budget.

**Acceptance criteria:**

- Specify mixture weights and exclusions.
- Audit benchmark overlap and document rights.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** Tiny/local model, synthetic media, or supplied recorded outputs/profiles; larger GPU or paid-provider runs are optional. Replay analysis cannot establish real hardware performance.

## M08-L02 — Plan training and checkpoints

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M08-L01](M08.md#m08-l01)

**Learning outcome:** Define a reproducible training run and recovery boundary.

**Topics:** causal and masked objectives; validation loss; scaling tradeoffs; checkpoints; recovery.

**Study estimate:** 2–4 hours guided study + 4–7 hours exercise. These are uncalibrated learner-effort estimates, not measured timings or an implementation schedule.

### Primary readings

- [LLM: Hugging Face LLM course](https://huggingface.co/learn/llm-course/en/chapter1/1) — Transformer architectures, tokenizers, fine-tuning, NLP, limitations.
- [ML: Made With ML course](https://madewithml.com/courses/mlops/) — Product and systems design, data, training, tracking, tests, versioning, operations.
- [SCALING: Scaling Laws for Neural Language Models](https://arxiv.org/abs/2001.08361) — Empirical relationships among model size, data and compute.
- [CHINCHILLA: Training Compute-Optimal Large Language Models](https://arxiv.org/abs/2203.15556) — Model and token allocation under a training budget.

### Interview question

What must a resumable checkpoint contain beyond model weights?

**A strong answer addresses:** Optimizer; scheduler; RNG; data position.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Run a tiny language-model training experiment, interrupt it and compare recovery with an uninterrupted baseline; use recorded checkpoint traces if compute is unavailable.

**Acceptance criteria:**

- Track tokens processed and validation loss.
- Compare resumed and uninterrupted runs within a declared tolerance.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** Tiny/local model, synthetic media, or supplied recorded outputs/profiles; larger GPU or paid-provider runs are optional. Replay analysis cannot establish real hardware performance.

## M08-L03 — Separate adaptation stages

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M08-L02](M08.md#m08-l02)

**Learning outcome:** Choose the smallest adaptation intervention supported by evidence.

**Topics:** continued pretraining; supervised fine-tuning; preference alignment; instruction data.

**Study estimate:** 2–3 hours guided study + 3–5 hours exercise. These are uncalibrated learner-effort estimates, not measured timings or an implementation schedule.

### Primary readings

- [LLM: Hugging Face LLM course](https://huggingface.co/learn/llm-course/en/chapter1/1) — Transformer architectures, tokenizers, fine-tuning, NLP, limitations.

### Interview question

When is domain-adaptive pretraining preferable to instruction tuning?

**A strong answer addresses:** Knowledge distribution; behavior objective; data requirements.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

**Acceptance criteria:**

**Evidence to submit:**

## M08-L04 — Release model artifacts responsibly

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M08-L03](M08.md#m08-l03)

**Learning outcome:** Specify evidence required before a model becomes a dependency.

**Topics:** model cards; licenses; provenance; benchmark contamination; reproducibility.

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are uncalibrated learner-effort estimates, not measured timings or an implementation schedule.

### Primary readings

- [ML: Made With ML course](https://madewithml.com/courses/mlops/) — Product and systems design, data, training, tracking, tests, versioning, operations.
- [NIST: NIST AI risk management framework](https://www.nist.gov/itl/ai-risk-management-framework) — Governance, risk identification, measurement and management.

### Interview question

Why is a benchmark score insufficient to approve a checkpoint?

**A strong answer addresses:** Task fit; data provenance; license; limitations.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Draft a release manifest linking weights, tokenizer, data versions and evaluation reports.

**Acceptance criteria:**

- Include rollback identity and intended uses.
- Distinguish observed results from unsupported claims.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** Tiny/local model, synthetic media, or supplied recorded outputs/profiles; larger GPU or paid-provider runs are optional. Replay analysis cannot establish real hardware performance.

## Module completion gate

Submit every lesson artifact, answer its interview question, and explain one failure-and-recovery case. A reviewer checks acceptance criteria and labels results as designed, simulated, replayed or measured. A plan or replay is not proof of production performance.

Readings support concepts. Larnix's lesson sequencing, scenarios, questions and acceptance criteria are original curriculum design. Recheck relevant source sections and pin implementation versions when writing the actual lessons.
