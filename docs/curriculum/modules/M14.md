## M14-L01 — Understand embedding objectives

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M03-L01](M03.md#m03-l01), [M07-L04](M07.md#m07-l04)

**Learning outcome:** Explain what an embedding model is trained to consider similar.

**Topics:** dense representations; contrastive learning; similarity; pooling; normalization.

**Study estimate:** 2–3 hours guided study + 2–4 hours exercise. These are uncalibrated learner-effort estimates, not measured timings or an implementation schedule.

### Primary readings

- [SEARCH: Sentence Transformers retrieve and rerank](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html) — Bi-encoder candidates and cross-encoder ranking.
- [LLM: Hugging Face LLM course](https://huggingface.co/learn/llm-course/en/chapter1/1) — Transformer architectures, tokenizers, fine-tuning, NLP, limitations.

### Interview question

Why might semantic similarity fail to retrieve an exact product code?

**A strong answer addresses:** Training objective; lexical precision; domain.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Create and run an embedding probe set with synonyms, negation and nearly identical equipment part numbers.

**Acceptance criteria:**

- Inspect nearest neighbors by slice.
- Distinguish semantic matches from identifier matches.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** Tiny/local model, synthetic media, or supplied recorded outputs/profiles; larger GPU or paid-provider runs are optional. Replay analysis cannot establish real hardware performance.

## M14-L04 — Manage embedding changes

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M14-L03](M14.md#m14-l03)

**Learning outcome:** Plan a migration without mixing incompatible vector spaces.

**Topics:** model versions; schema compatibility; backfills; dual indexes; rollback.

**Study estimate:** 2–3 hours guided study + 4–6 hours exercise. These are uncalibrated learner-effort estimates, not measured timings or an implementation schedule.

### Primary readings

- [PGVECTOR: pgvector documentation](https://github.com/pgvector/pgvector) — Postgres vector search, filtering, approximate indexes, hybrid search.
- [ML: Made With ML course](https://madewithml.com/courses/mlops/) — Product and systems design, data, training, tracking, tests, versioning, operations.

### Interview question

Can old and new embeddings share one index if dimensions match?

**A strong answer addresses:** Coordinate systems; normalization; model version.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Build a dual-index migration prototype with shadow queries and versioned records.

**Acceptance criteria:**

- Prevent cross-version comparisons.
- Define cutover and rollback using measured retrieval quality.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** Tiny/local model, synthetic media, or supplied recorded outputs/profiles; larger GPU or paid-provider runs are optional. Replay analysis cannot establish real hardware performance.
