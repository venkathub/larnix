## M20-L01 — Design useful tool contracts

**Prerequisites:** [M19-L04](M19.md#m19-l04), [M02-L04](M02.md#m02-l04)

**Learning outcome:** Create tools whose behavior and limits are clear to both model and caller.

**Topics:** tool descriptions; argument schemas; result schemas; granularity; discoverability.

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are learner-effort estimates, not an implementation schedule.

### Primary readings

- [STRUCT: OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) — Schema constraints, refusals, parsing, tool versus response schemas.
- [AGENT: Anthropic building effective agents](https://www.anthropic.com/engineering/building-effective-agents) — Workflow patterns, autonomy, tool design, complexity tradeoffs.

### Interview question

Why can one universal tool be harder to use than several narrow tools?

**A strong answer addresses:** Ambiguity; permissions; validation; search space.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Implement lookup, quote and draft-return tools with typed input/output contracts and controlled fixture data.

**Acceptance criteria:**

- Reject invalid arguments.
- Document units, pagination and missing-record behavior.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

## M20-L02 — Enforce authority outside the model

**Prerequisites:** [M20-L01](M20.md#m20-l01), [M30-L02](M30.md#m30-l02)

**Learning outcome:** Check the caller's authority before any side effect.

**Topics:** authentication; authorization; least privilege; read/write separation; approvals.

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are learner-effort estimates, not an implementation schedule.

### Primary readings

- [OWASP: OWASP LLM application risks](https://genai.owasp.org/llm-top-10/) — Injection, disclosure, supply chain, poisoning, outputs, agency, consumption.
- [MCP: Model Context Protocol specification](https://modelcontextprotocol.io/specification/2026-07-28) — Versioned protocol, tools, resources, prompts, capabilities, authorization.

### Interview question

Why is a model-generated approval flag insufficient authorization?

**A strong answer addresses:** Untrusted arguments; identity; policy enforcement.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Implement a server-side authorization policy for inventory reads and refund drafts, then test forged identity and approval fields.

**Acceptance criteria:**

- Deny forged identity and approval fields.
- Audit the principal and authorized operation.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

## M20-L03 — Make side effects recoverable

**Prerequisites:** [M20-L02](M20.md#m20-l02)

**Learning outcome:** Prevent duplicate business actions across uncertain tool outcomes.

**Topics:** idempotency; request keys; retries; receipts; compensation; partial failure.

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are learner-effort estimates, not an implementation schedule.

### Primary readings

- [TEMPORAL: Temporal workflow execution](https://docs.temporal.io/workflow-execution) — Durable execution, workflow lifecycle, failure recovery.
- [SRE: Google SRE book](https://sre.google/sre-book/table-of-contents/) — Service objectives, overload, monitoring, incident response, reliability testing.

### Interview question

What should happen after a timeout on a successful refund request?

**A strong answer addresses:** Status lookup; stable operation ID; duplicate suppression.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Implement a mock refund tool and inject lost-response and repeated-call failures.

**Acceptance criteria:**

- Record one logical refund per key.
- Distinguish failed, completed and unknown outcomes.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

## M20-L04 — Contain tool execution

**Prerequisites:** [M20-L03](M20.md#m20-l03)

**Learning outcome:** Bound resource use and isolate untrusted tool results.

**Topics:** sandboxing; filesystem access; network egress; output limits; error contracts; browser and computer-use boundaries.

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are learner-effort estimates, not an implementation schedule.

### Primary readings

- [OWASP: OWASP LLM application risks](https://genai.owasp.org/llm-top-10/) — Injection, disclosure, supply chain, poisoning, outputs, agency, consumption.
- [AGENT: Anthropic building effective agents](https://www.anthropic.com/engineering/building-effective-agents) — Workflow patterns, autonomy, tool design, complexity tradeoffs.

### Interview question

How can a read-only tool still introduce risk?

**A strong answer addresses:** Sensitive output; injection; resource exhaustion.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Build a sandboxed document-inspection tool with path, size, network and time restrictions.

**Acceptance criteria:**

- Reject disallowed paths and network destinations.
- Truncate safely and label tool output as untrusted.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

## Module completion gate

Submit all four lesson artifacts, answer the four interview questions, and explain one failure-and-recovery case. A reviewer checks acceptance criteria and labels results as designed, simulated, replayed or measured. A plan or replay is not proof of production performance.

Readings support concepts. Larnix's lesson sequencing, scenarios, questions and acceptance criteria are original curriculum design. Recheck relevant source sections and pin implementation versions when writing the actual lessons.
