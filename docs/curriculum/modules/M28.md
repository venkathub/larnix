## Module outcomes

- Set service objectives that distinguish infrastructure success from task success.
- Bound demand and stop failures spreading across dependencies.
- Choose consistency and compensation rules for multi-step business actions.
- Offer a defined reduced service without fabricating success.

## M28-L01 — Define reliability targets

**Prerequisites:** [M02-L04](M02.md#m02-l04), [M09-L04](M09.md#m09-l04), [M27-L01](M27.md#m27-l01)

**Learning outcome:** Set service objectives that distinguish infrastructure success from task success.

**Topics:** SLIs; SLOs; error budgets; availability; latency; durability; quality boundaries.

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are learner-effort estimates, not an implementation schedule.

### Primary readings

- [SRE: Google SRE book](https://sre.google/sre-book/table-of-contents/) — Service objectives, overload, monitoring, incident response, reliability testing.

### Interview question

Is HTTP 200 a sufficient success indicator for an AI endpoint?

**A strong answer addresses:** Semantic validity; latency; completed work.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Write an SLO specification for interactive answers and background document ingestion.

**Acceptance criteria:**

- Define measurement windows and exclusions.
- Separate latency and valid-result objectives.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

**Acceptance criteria:**

## M28-L04 — Design graceful degradation

**Prerequisites:** [M28-L03](M28.md#m28-l03)

**Learning outcome:** Offer a defined reduced service without fabricating success.

**Topics:** fallbacks; stale reads; reduced capability; failover; disaster recovery; runbooks.

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are learner-effort estimates, not an implementation schedule.

### Primary readings

- [SRE: Google SRE book](https://sre.google/sre-book/table-of-contents/) — Service objectives, overload, monitoring, incident response, reliability testing.

### Interview question

When is failing closed better than switching to a weaker model?

**A strong answer addresses:** Authorization; action risk; semantic compatibility.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Write an outage runbook covering provider failure, index outage and restoration.

**Acceptance criteria:**

- State degraded behavior per dependency.
- Include recovery verification and data-loss assumptions.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

## Module completion gate

Submit all four lesson artifacts, answer the four interview questions, and explain one failure-and-recovery case. A reviewer checks acceptance criteria and labels results as designed, simulated, replayed or measured. A plan or replay is not proof of production performance.

Readings support concepts. Larnix's lesson sequencing, scenarios, questions and acceptance criteria are original curriculum design. Recheck relevant source sections and pin implementation versions when writing the actual lessons.
