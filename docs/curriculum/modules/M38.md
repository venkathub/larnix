## Module outcomes

- Separate transcription quality from downstream task completion.
- Define when the assistant listens, speaks and stops speaking.
- Make tool delays and action status understandable in spoken interaction.
- Measure conversation outcomes across representative acoustic conditions.
- Build a language-specific evaluation plan that does not hide weak languages inside a pooled average.

## M38-L01 — Understand the speech pipeline

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M09-L04](M09.md#m09-l04), [M19-L04](M19.md#m19-l04), [M25-L04](M25.md#m25-l04)

**Learning outcome:** Separate transcription quality from downstream task completion.

**Topics:** sampling; codecs; ASR; TTS; diarization; WER; speech-to-speech.

**Study estimate:** 2–3 hours guided study + 3–5 hours exercise. These are uncalibrated learner-effort estimates, not measured timings or an implementation schedule.

### Primary readings

- [ASR: Transformers automatic speech recognition](https://huggingface.co/docs/transformers/main/en/tasks/asr) — Audio preprocessing, transcription models and word error rate.
- [VOICE: OpenAI voice agent guide](https://developers.openai.com/api/docs/guides/voice-agents) — Chained and speech-to-speech architectures, interruptions, task evaluation.

### Interview question

Can a system with low word error rate still fail a booking task?

**A strong answer addresses:** Critical entities; turn context; intent; actions.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Create an audio test set with equipment names, dates and noisy backgrounds; score recorded or locally generated transcripts.

**Acceptance criteria:**

- Report entity errors as well as WER.
- Document recording permissions and synthetic alternatives.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** Tiny/local model, synthetic media, or supplied recorded outputs/profiles; larger GPU or paid-provider runs are optional. Replay analysis cannot establish real hardware performance.

## M38-L05 — Evaluate multilingual and low-resource behavior

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M38-L04](M38.md#m38-l04)

**Learning outcome:** Build a language-specific evaluation plan that does not hide weak languages inside a pooled average.

**Topics:** multilingual evaluation; low-resource languages; code switching; tokenization cost; translation quality; locale-specific safety and moderation.

**Study estimate:** 2–3 hours guided study + 3–5 hours exercise. These are uncalibrated learner-effort estimates, not measured timings or an implementation schedule.

### Primary readings

- [NLLB: No Language Left Behind](https://arxiv.org/abs/2207.04672) — Low-resource translation, language coverage and evaluation.
- [ASR: Transformers automatic speech recognition](https://huggingface.co/docs/transformers/main/en/tasks/asr) — Audio preprocessing, transcription models and word error rate.
- [HAX: Microsoft human AI interaction guidelines](https://www.microsoft.com/en-us/haxtoolkit/ai-guidelines/) — User expectations, corrections, feedback, recovery.

### Interview question

Why is translating an English test set insufficient evidence for a low-resource deployment?

**A strong answer addresses:** Cultural and lexical coverage; Native-speaker review and label reliability; Per-language errors and token costs.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Create a reviewed bilingual ticket fixture including code switching; compare original-language and translated processing and log missing language expertise.

**Acceptance criteria:**

- Report each language separately with sample sizes.
- Include meaning loss and moderation failures.
- Do not label machine-translated references as native-speaker ground truth.

**Evidence to submit:**

- Versioned code or analysis with environment and input checksum.
- Hand-checkable baseline and comparison outputs.
- Injected failure, diagnosis and corrected rerun.
- Decision, resource assumptions and limitations.

**Resources:** Small original CPU/local fixture; hosted services and accelerators optional. Record simulation, replay or measurement honestly.

## Module completion gate

Submit every lesson artifact, answer its interview question, and explain one failure-and-recovery case. A reviewer checks acceptance criteria and labels results as designed, simulated, replayed or measured. A plan or replay is not proof of production performance.
