## M24-L01 — Justify multiple agents

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M21-L04](M21.md#m21-l04), [M23-L04](M23.md#m23-l04)

**Learning outcome:** Use multiple agents only where a measurable coordination benefit exists.

**Topics:** specialization; decomposition; coordination overhead; shared context; single-agent baseline.

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are uncalibrated learner-effort estimates, not measured timings or an implementation schedule.

### Primary readings

- [AGENT: Anthropic building effective agents](https://www.anthropic.com/engineering/building-effective-agents) — Workflow patterns, autonomy, tool design, complexity tradeoffs.
- [REACT: ReAct: Synergizing Reasoning and Acting in Language Models](https://arxiv.org/abs/2210.03629) — Interleaving reasoning and environment actions.
- [TAU: tau-bench original paper](https://arxiv.org/abs/2406.12045) — Stateful tool-agent-user tasks and repeated reliability.

### Interview question

Why might more agents lower task accuracy?

**A strong answer addresses:** Error propagation; redundant work; inconsistent state.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Specify single-agent and specialist-agent designs for equipment incident investigation.

**Acceptance criteria:**

- Use matched task sets.
- Compare coordination cost, latency and verified outcomes.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

## M24-L04 — Contain coordination failures

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M24-L03](M24.md#m24-l03)

**Learning outcome:** Bound distributed agent work and recover from missing participants.

**Topics:** timeouts; partial results; duplicate tasks; budget allocation; cyclic delegation.

**Study estimate:** 2–3 hours guided study + 4–6 hours exercise. These are uncalibrated learner-effort estimates, not measured timings or an implementation schedule.

### Primary readings

- [A2A: A2A specification](https://a2a-protocol.org/latest/specification/) — Agent discovery, messages, tasks, artifacts, transports, authentication.
- [SRE: Google SRE book](https://sre.google/sre-book/table-of-contents/) — Service objectives, overload, monitoring, incident response, reliability testing.

### Interview question

How would you prevent agents delegating the same task forever?

**A strong answer addresses:** Depth limits; task IDs; budgets; ownership.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Run an orchestration fault drill with an unavailable specialist, duplicate tasks and conflicting results.

**Acceptance criteria:**

- Cap fan-out and delegation depth.
- Return an explicit partial or failed outcome with traceable evidence.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

## Module completion gate

Submit every lesson artifact, answer its interview question, and explain one failure-and-recovery case. A reviewer checks acceptance criteria and labels results as designed, simulated, replayed or measured. A plan or replay is not proof of production performance.

Readings support concepts. Larnix's lesson sequencing, scenarios, questions and acceptance criteria are original curriculum design. Recheck relevant source sections and pin implementation versions when writing the actual lessons.
