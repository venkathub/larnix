[All modules](../INDEX.md) · [Learning path](../LEARNING_PATH.md) · [Source register](../SOURCES.md)

**Entry prerequisites:** [M02-L04](M02.md#m02-l04), [M04-L02](M04.md#m04-l02)

## Module outcomes

- Specify data contracts across training and serving pipelines.
- Create a labeling process with measurable quality controls.
- Trace a model result to the exact source records and transformations.
- Propagate data changes without silently retaining forbidden records.

## M06-L01 — Define dataset contracts

**Prerequisites:** [M02-L04](M02.md#m02-l04), [M04-L02](M04.md#m04-l02)

**Learning outcome:** Specify data contracts across training and serving pipelines.

**Topics:** schemas; validation; ETL and ELT; batch; streaming; feature stores.

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are learner-effort estimates, not an implementation schedule.

### Primary readings

- [DATA: Hugging Face Datasets](https://huggingface.co/docs/datasets/index) — Loading, mapping, streaming, dataset processing.
- [ML: Made With ML course](https://madewithml.com/courses/mlops/) — Product and systems design, data, training, tracking, tests, versioning, operations.

### Interview question

What causes training-serving skew even with identical code?

**A strong answer addresses:** Source timing; feature freshness; schema drift.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Build a fixture-based rental-event ingestion pipeline with schema checks, late events and point-in-time feature joins.

**Acceptance criteria:**

- Include schema-change and late-event tests.
- Specify point-in-time feature joins.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

## M06-L02 — Curate reliable labels

**Prerequisites:** [M06-L01](M06.md#m06-l01)

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are learner-effort estimates, not an implementation schedule.

### Interview question

**A strong answer addresses:** Generator bias; overlap; missing real-world cases.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Create and label an original synthetic ticket corpus using written guidelines, adjudication and duplicate detection.

**Acceptance criteria:**

- Measure annotator agreement.
- Separate synthetic training data from human holdout cases.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

## M06-L04 — Operate the data lifecycle

**Prerequisites:** [M06-L03](M06.md#m06-l03)

**Learning outcome:** Propagate data changes without silently retaining forbidden records.

**Topics:** PII minimization; retention; deletion; distribution shift; quality alerts.

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are learner-effort estimates, not an implementation schedule.

### Primary readings

- [NIST: NIST AI risk management framework](https://www.nist.gov/itl/ai-risk-management-framework) — Governance, risk identification, measurement and management.
- [ML: Made With ML course](https://madewithml.com/courses/mlops/) — Product and systems design, data, training, tracking, tests, versioning, operations.

### Interview question

Why is deleting a raw file insufficient for an AI system?

**A strong answer addresses:** Derived artifacts; caches; indexes; backups.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Implement deletion propagation across a toy raw store, derived dataset and cache; document the remaining retention policy.

**Acceptance criteria:**

- Trace one deletion end to end.
- Define an alert owner and a drift-investigation decision.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

## Module completion gate

Submit all four lesson artifacts, answer the four interview questions, and explain one failure-and-recovery case. A reviewer checks acceptance criteria and labels results as designed, simulated, replayed or measured. A plan or replay is not proof of production performance.

Readings support concepts. Larnix's lesson sequencing, scenarios, questions and acceptance criteria are original curriculum design. Recheck relevant source sections and pin implementation versions when writing the actual lessons.
