# M29 — Deployment and delivery

[All modules](../INDEX.md) · [Learning path](../LEARNING_PATH.md) · [Source register](../SOURCES.md) · [Teaching design](../TEACHING_DESIGN.md)

**Status:** planned · **Depth:** core · **Track:** T5

**Entry prerequisites:** [M02-L04](M02.md#m02-l04), [M25-L04](M25.md#m25-l04), [M28-L04](M28.md#m28-l04)

Four lesson specifications follow. Each lesson will use a concrete problem, prediction, interactive explanation, worked example, inline checks and failure investigation before production and interview practice. Follow the teaching design for accessibility and original visual treatment. These interactions are planned, not implemented. Complete the evidence package for each exercise; live deployment is not required. Later lessons may introduce an additional cross-module prerequisite.

## Module outcomes

- Specify a build that reproduces code, configuration and model dependencies.
- Place deterministic and probabilistic checks at appropriate release stages.
- Roll out code and model changes while preserving recoverability.
- Choose deployment complexity from workload and team needs.

## M29-L01 — Package reproducible services

**Prerequisites:** [M02-L04](M02.md#m02-l04), [M25-L04](M25.md#m25-l04), [M28-L04](M28.md#m28-l04)

**Learning outcome:** Specify a build that reproduces code, configuration and model dependencies.

**Topics:** containers; dependency locks; environment configuration; artifacts; SBOMs.

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are learner-effort estimates, not an implementation schedule.

### Primary readings

- [DOCKER: Docker getting started](https://docs.docker.com/get-started/) — Containers, images, reproducible environments.
- [ML: Made With ML course](https://madewithml.com/courses/mlops/) — Product and systems design, data, training, tracking, tests, versioning, operations.

### Interview question

Why is a container image alone insufficient to reproduce an AI answer?

**A strong answer addresses:** External models; prompts; indexes; data versions.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Package a mock policy API and ingestion worker in reproducible containers with a version manifest.

**Acceptance criteria:**

- Pin application artifacts.
- Record external model and index versions without bundling credentials.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

**Acceptance criteria:**

- Versioned artifact or design specification.

## M29-L04 — Operate across environments

**Prerequisites:** [M29-L03](M29.md#m29-l03)

**Learning outcome:** Choose deployment complexity from workload and team needs.

**Topics:** managed services; self-hosting; Kubernetes; autoscaling; IaC; environment parity.

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are learner-effort estimates, not an implementation schedule.

### Primary readings

- [DOCKER: Docker getting started](https://docs.docker.com/get-started/) — Containers, images, reproducible environments.
- [K8S: Kubernetes deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/) — Rollouts, replicas, rollout status and rollback.
- [SRE: Google SRE book](https://sre.google/sre-book/table-of-contents/) — Service objectives, overload, monitoring, incident response, reliability testing.

### Interview question

When is Kubernetes excessive for an AI application?

**A strong answer addresses:** Traffic; team capacity; operational burden; alternatives.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Write a deployment decision for a small team and a later scale-up path.

**Acceptance criteria:**

- Compare operating cost and failure recovery.
- Define load-test and restore acceptance criteria.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

## Module completion gate

Submit all four lesson artifacts, answer the four interview questions, and explain one failure-and-recovery case. A reviewer checks acceptance criteria and labels results as designed, simulated, replayed or measured. A plan or replay is not proof of production performance.

Readings support concepts. Larnix's lesson sequencing, scenarios, questions and acceptance criteria are original curriculum design. Recheck relevant source sections and pin implementation versions when writing the actual lessons.
