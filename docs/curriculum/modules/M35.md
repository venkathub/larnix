Follow the teaching design for accessibility and original visual treatment. Delivery status is stated per lesson; a preview is not a completed lab. Complete the evidence package for each exercise; live deployment is not required. Later lessons may introduce an additional cross-module prerequisite.

## Module outcomes

- Explain why prompt and output lengths stress serving differently.
- Choose scheduling and caching policies from measured workload behavior.
- Evaluate speedups against memory use and output quality.
- Distinguish fitting one model from scaling concurrent users.
- Identify whether transfers, memory traffic or compute dominate a stated workload before choosing an optimization.
- Choose one target runtime, export a model and test prediction parity before claiming a device deployment.

## M35-L01 — Model inference costs

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M07-L04](M07.md#m07-l04), [M28-L04](M28.md#m28-l04), [M32-L04](M32.md#m32-l04)

**Learning outcome:** Explain why prompt and output lengths stress serving differently.

**Topics:** prefill; decode; KV cache; TTFT; inter-token latency; throughput; GPU memory.

**Study estimate:** 2–3 hours guided study + 3–5 hours exercise. These are learner-effort estimates, not an implementation schedule.

**Estimate basis:** Study model inference costs; build or analyze: Run a small-model serving benchmark or analyze supplied traces across prompt length, output length and concurrency. Verify: Report TTFT, inter-token latency and end-to-end percentiles. Stated prerequisites met; small local fixture or explicitly labeled replay; excludes large training runs and cloud provisioning. Confidence: low; editorial estimate, not learner-measured.

### Primary readings

- [VLLM: vLLM documentation](https://docs.vllm.ai/en/latest/) — Serving, batching, quantization, caching, speculative decoding, parallelism.
- [PAGED: PagedAttention original paper](https://arxiv.org/abs/2309.06180) — KV memory management and serving throughput.

### Interview question

Why can a server have high tokens per second but poor interactive latency?

**A strong answer addresses:** Batching; queueing; prefill interference; tail latency.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Run a small-model serving benchmark or analyze supplied traces across prompt length, output length and concurrency.

**Acceptance criteria:**

- Report TTFT, inter-token latency and end-to-end percentiles.
- Record hardware and warm-up assumptions.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** Tiny/local model, synthetic media, or supplied recorded outputs/profiles; larger GPU or paid-provider runs are optional. Replay analysis cannot establish real hardware performance.

## M35-L05 — Understand hardware before optimizing kernels

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M35-L04](M35.md#m35-l04)

**Learning outcome:** Identify whether transfers, memory traffic or compute dominate a stated workload before choosing an optimization.

**Topics:** CPU GPU NPU roles; GPU memory hierarchy; bandwidth versus compute; precision and tensor operations; host device transfer; profiling and warmup.

**Study estimate:** 2–4 hours guided study + 3–5 hours exercise. These are learner-effort estimates, not an implementation schedule.

**Estimate basis:** Study understand hardware before optimizing kernels; build or analyze: Build a tensor-operation cost worksheet and profile a small workload on available hardware; compare against a recorded GPU trace if no accelerator is available. Verify: Separate initialization, transfer and steady-state work. Stated prerequisites met; small local fixture or explicitly labeled replay; excludes large training runs and cloud provisioning. Confidence: low; editorial estimate, not learner-measured.

### Primary readings

- [CUDA: CUDA Programming Guide](https://docs.nvidia.com/cuda/cuda-programming-guide/index.html) — GPU execution, memory hierarchy, transfers and profiling context.
- [FLASH: FlashAttention](https://arxiv.org/abs/2205.14135) — Exact attention with reduced memory traffic.
- [PT: PyTorch learning basics](https://docs.pytorch.org/tutorials/beginner/basics/intro.html) — Tensors, data loaders, autograd, optimization, persistence.

### Interview question

Why can a GPU benchmark be slower despite more theoretical FLOPS?

**A strong answer addresses:** Small batches and launch overhead; Transfers and synchronization; Warmup, timing and hardware disclosure.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Build a tensor-operation cost worksheet and profile a small workload on available hardware; compare against a recorded GPU trace if no accelerator is available.

**Acceptance criteria:**

- Separate initialization, transfer and steady-state work.
- Report hardware and precision.
- Label trace analysis as replayed and avoid extrapolating CPU timing to GPU performance.

**Evidence to submit:**

- Versioned code or analysis with environment and input checksum.
- Hand-checkable baseline and comparison outputs.
- Injected failure, diagnosis and corrected rerun.
- Decision, resource assumptions and limitations.

**Resources:** Small original CPU/local fixture; hosted services and accelerators optional. Record simulation, replay or measurement honestly.

## M35-L06 — Export and validate models on constrained devices

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M35-L05](M35.md#m35-l05), [M29-L07](M29.md#m29-l07)

**Learning outcome:** Choose one target runtime, export a model and test prediction parity before claiming a device deployment.

**Topics:** ONNX export; TensorRT; Core ML; LiteRT and TensorFlow Lite; ExecuTorch; operator support; quantization parity; edge privacy and thermal limits.

**Study estimate:** 2–4 hours guided study + 4–7 hours exercise. These are learner-effort estimates, not an implementation schedule.

**Estimate basis:** Study export and validate models on constrained devices; build or analyze: Export one tiny trained model to ONNX Runtime or ExecuTorch and compare with the source runtime; prepare a target matrix for TensorRT, Core ML and LiteRT. Verify: Set accuracy tolerances before conversion. Stated prerequisites met; small local fixture or explicitly labeled replay; excludes large training runs and cloud provisioning. Confidence: low; editorial estimate, not learner-measured.

### Primary readings

- [ONNX: ONNX Runtime model optimizations](https://onnxruntime.ai/docs/performance/model-optimizations/) — Model optimization and runtime execution constraints.
- [EXECUTORCH: ExecuTorch documentation](https://docs.pytorch.org/executorch/stable/index.html) — Export and deployment to constrained devices.
- [COREML: Apple Core ML documentation](https://developer.apple.com/documentation/coreml) — Apple device deployment; entry page requires JavaScript for details.
- [LITERT: Google LiteRT documentation](https://developers.google.com/edge/litert) — On-device deployment; TensorFlow Lite lineage and current runtime choices.
- [TENSORRT: NVIDIA TensorRT documentation](https://docs.nvidia.com/deeplearning/tensorrt/latest/) — NVIDIA inference optimization and backend compatibility.

### Interview question

Why can successful export still fail to produce an acceptable mobile app?

**A strong answer addresses:** Unsupported operator or fallback; Numerical drift after conversion; Device memory, startup and thermal limits.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Export one tiny trained model to ONNX Runtime or ExecuTorch and compare with the source runtime; prepare a target matrix for TensorRT, Core ML and LiteRT.

**Acceptance criteria:**

- Set accuracy tolerances before conversion.
- Exercise unsupported input shapes and operator compatibility.
- State which target was actually run; desktop export is not a phone latency measurement.

**Evidence to submit:**

- Versioned code or analysis with environment and input checksum.
- Hand-checkable baseline and comparison outputs.
- Injected failure, diagnosis and corrected rerun.
- Decision, resource assumptions and limitations.

**Resources:** Small original CPU/local fixture; hosted services and accelerators optional. Record simulation, replay or measurement honestly.
