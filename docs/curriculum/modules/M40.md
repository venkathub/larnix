## M40-L01 — Design search and recommendations

**Prerequisites:** [M04-L04](M04.md#m04-l04), [M17-L04](M17.md#m17-l04), [M21-L04](M21.md#m21-l04), [M26-L04](M26.md#m26-l04), [M29-L04](M29.md#m29-l04), [M30-L04](M30.md#m30-l04)

**Learning outcome:** Choose a recommendation architecture and guard against biased feedback.

**Topics:** candidate generation; ranking; collaborative filtering; content features; cold start; feedback loops.

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are learner-effort estimates, not an implementation schedule.

### Primary readings

- [RECSYS: Google recommendation systems course](https://developers.google.com/machine-learning/recommendation) — Candidate generation, scoring, re-ranking and collaborative filtering.

### Interview question

Why can click-through optimization reduce recommendation usefulness?

**A strong answer addresses:** Position bias; short-term reward; user value.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Build a small equipment recommendation prototype for synthetic rental histories with popularity and cold-start baselines.

**Acceptance criteria:**

- Use time-aware evaluation.
- Compare popularity and personalized baselines and measure coverage.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

## M40-L02 — Combine prediction and language

**Prerequisites:** [M40-L01](M40.md#m40-l01)

**Learning outcome:** Use predictive models for quantities and language models for grounded explanation.

**Topics:** forecasting; anomaly detection; temporal validation; uncertainty; explanatory interfaces.

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are learner-effort estimates, not an implementation schedule.

### Primary readings

- [FORECAST: Forecasting: Principles and Practice, author textbook](https://otexts.com/fpp3/) — Time-series patterns, temporal evaluation, forecasting baselines and uncertainty.
- [SK: scikit-learn model selection](https://scikit-learn.org/stable/model_selection.html) — Splitting, cross-validation, metrics, tuning.

### Interview question

Why should a language model not invent the numerical forecast it explains?

**A strong answer addresses:** Source of truth; uncertainty; verifiable computation.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Build demand forecasting with a seasonal naive baseline and evidence-linked explanations using synthetic time-series data.

**Acceptance criteria:**

- Use rolling-origin evaluation.
- Preserve prediction intervals and detect invented numbers.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

## M40-L04 — Build operational and coding assistants

**Prerequisites:** [M40-L03](M40.md#m40-l03)

**Learning outcome:** Choose action boundaries and executable validation for operational assistants.

**Topics:** support resolution; incident triage; code repair; sandbox execution; bounded autonomy.

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are learner-effort estimates, not an implementation schedule.

### Primary readings

- [SWE: SWE-bench datasets](https://www.swebench.com/SWE-bench/guides/datasets/) — Repository tasks, benchmark variants, reproducible coding evaluation.
- [AGENT: Anthropic building effective agents](https://www.anthropic.com/engineering/building-effective-agents) — Workflow patterns, autonomy, tool design, complexity tradeoffs.
- [OWASP: OWASP LLM application risks](https://genai.owasp.org/llm-top-10/) — Injection, disclosure, supply chain, poisoning, outputs, agency, consumption.

### Interview question

Why should a coding assistant's final message not define success?

**A strong answer addresses:** Tests; diffs; environment state; side effects.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Build a sandbox assistant that diagnoses and repairs a deliberately broken mock rental API.

**Acceptance criteria:**

- Require a minimal reviewed diff and relevant tests.
- Audit file access and forbid production credentials.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

## Module completion gate

Submit all four lesson artifacts, answer the four interview questions, and explain one failure-and-recovery case. A reviewer checks acceptance criteria and labels results as designed, simulated, replayed or measured. A plan or replay is not proof of production performance.

Readings support concepts. Larnix's lesson sequencing, scenarios, questions and acceptance criteria are original curriculum design. Recheck relevant source sections and pin implementation versions when writing the actual lessons.
