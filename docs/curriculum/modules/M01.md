# M01 — AI product engineering

[All modules](../INDEX.md) · [Learning path](../LEARNING_PATH.md) · [Source register](../SOURCES.md) · [Teaching design](../TEACHING_DESIGN.md)

**Status:** in_progress · **Depth:** core · **Track:** T1

**Entry prerequisites:** Entry module; see the readiness guide in the curriculum overview.

4 lesson specifications follow. Each lesson will use a concrete problem, prediction, interactive explanation, worked example, inline checks and failure investigation before production and interview practice. Follow the teaching design for accessibility and original visual treatment. Delivery status is stated per lesson; a preview is not a completed lab. Complete the evidence package for each exercise; live deployment is not required. Later lessons may introduce an additional cross-module prerequisite.

## Module outcomes

- Turn a vague request into a decision and a measurable non-AI baseline.
- Translate business goals into quality and cost constraints.
- Define when an assistant should answer, ask, abstain or escalate.
- Write an architecture decision with reversible release boundaries.

## M01-L01 — Frame a useful decision

**Delivery:** preview · full lesson contract: not_met · interaction: illustrated_cases · artifact: learner_starter

**Prerequisites:** Entry readiness only.

**Learning outcome:** Turn a vague request into a decision and a measurable non-AI baseline.

**Topics:** user jobs; failure costs; rules versus ML versus generation; baseline.

**Study estimate:** 1–1 hours guided study + 1–2 hours exercise. These are learner-effort estimates, not an implementation schedule.

**Estimate basis:** Study frame a useful decision; build or analyze: Write a decision brief for a fictional equipment-rental support desk, including a rules baseline. Verify: Name the user and decision. Stated prerequisites met; small local fixture or explicitly labeled replay; excludes large training runs and cloud provisioning. Confidence: low; editorial estimate, not learner-measured.

### Primary readings

- [FRAME: Google ML problem framing](https://developers.google.com/machine-learning/problem-framing) — Problem suitability, objectives, success metrics.

### Interview question

When would you reject an LLM for ticket routing?

**A strong answer addresses:** Task frequency; error asymmetry; baseline evidence.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Write a decision brief for a fictional equipment-rental support desk, including a rules baseline.

**Acceptance criteria:**

- Name the user and decision.
- Define two costly failure cases and one reason to stop.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

## Module completion gate

Submit every lesson artifact, answer its interview question, and explain one failure-and-recovery case. A reviewer checks acceptance criteria and labels results as designed, simulated, replayed or measured. A plan or replay is not proof of production performance.

Readings support concepts. Larnix's lesson sequencing, scenarios, questions and acceptance criteria are original curriculum design. Recheck relevant source sections and pin implementation versions when writing the actual lessons.
