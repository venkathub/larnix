## M09-L01 — Define provider-neutral requests

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M02-L04](M02.md#m02-l04), [M07-L04](M07.md#m07-l04)

**Learning outcome:** Specify a narrow adapter without hiding provider differences.

**Topics:** message roles; model capabilities; adapters; token limits; response metadata.

**Study estimate:** 1–2 hours guided study + 2–4 hours exercise. These are uncalibrated learner-effort estimates, not measured timings or an implementation schedule.

### Primary readings

- [CHAT: Hugging Face chat templates](https://huggingface.co/docs/transformers/main/en/chat_templating) — Role serialization, generation prompts, template compatibility.
- [STRUCT: OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) — Schema constraints, refusals, parsing, tool versus response schemas.
- [APIS: OpenAI Responses API migration and contracts](https://developers.openai.com/api/docs/guides/migrate-to-responses) — Request/response structures, items, state and API contract differences.

### Interview question

What breaks when every provider is forced into the same feature contract?

**A strong answer addresses:** Capability mismatch; silent degradation; error semantics.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Implement adapters for two mock providers with different structured-output and tool capabilities.

**Acceptance criteria:**

- Reject unsupported options explicitly.
- Preserve model identity and usage metadata.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

## M09-L02 — Handle streaming as a protocol

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M09-L01](M09.md#m09-l01)

**Learning outcome:** Define a stream state machine that distinguishes partial and completed responses.

**Topics:** incremental events; partial output; cancellation; terminal events; backpressure; chat UI state; incremental rendering; accessible live regions; cancel and retry UX; demo UI versus production client.

**Study estimate:** 2–3 hours guided study + 3–5 hours exercise. These are uncalibrated learner-effort estimates, not measured timings or an implementation schedule.

### Primary readings

- [PY: Python asyncio](https://docs.python.org/3/library/asyncio.html) — Tasks, cancellation, queues, streams.
- [STRUCT: OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) — Schema constraints, refusals, parsing, tool versus response schemas.
- [STREAM: OpenAI streaming responses](https://developers.openai.com/api/docs/guides/streaming-responses) — Typed stream events, incremental output, completion and error handling.
- [HAX: Microsoft human AI interaction guidelines](https://www.microsoft.com/en-us/haxtoolkit/ai-guidelines/) — User expectations, corrections, feedback, recovery.

### Interview question

Can a partially streamed JSON object be treated as valid output?

**A strong answer addresses:** Completion state; parser state; validation.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Build a stream consumer and inject delayed chunks, mid-stream failure and client cancellation.

**Acceptance criteria:**

- Never commit partial business data.
- Record one terminal outcome and release resources.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** CPU/local fixtures or a mocked provider; live service use is optional.

**Learning outcome:** Define compatibility tests before swapping a provider or model.
