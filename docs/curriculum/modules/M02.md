## Module outcomes

- Trace a small rental-price program, predict its output and run it to explain any mismatch.
- Represent a few rental tickets in collections, round-trip them through files and explain which fields need conversion.
- Diagnose a failed rental calculation from its traceback and write tests that distinguish valid input from an explicit rejection.
- Reproduce a small rental summary in a fresh environment, move its notebook logic into a script and commit the intended file change.
- Specify a small typed component that runs reproducibly outside a notebook.
- Compute daily equipment costs with explicit shapes and verify that a vectorized result agrees with a loop.
- Join rentals and equipment rates without silently multiplying observations or dropping unknown equipment.
- Produce a reproducible dataset report whose plots expose missingness and unequal sample sizes.
- Separate transport failures from invalid application data.
- Design bounded concurrency and propagate cancellation through a request.
- Define atomic writes and tests for partial failure.

## M02-L08 — Read and run a Python program

**Delivery:** preview · full lesson contract: not_met · interaction: illustrated_cases · artifact: none

**Prerequisites:** Entry readiness only.

**Learning outcome:** Trace a small rental-price program, predict its output and run it to explain any mismatch.

**Topics:** values and types; variables; control flow; functions; reading a program top to bottom.

**Study estimate:** 1–2 hours guided study + 2–3 hours exercise. These are uncalibrated learner-effort estimates, not measured timings or an implementation schedule.

### Primary readings

- [PYINTRO: Python: An informal introduction to Python](https://docs.python.org/3.12/tutorial/introduction.html) — Values, numeric and text types, expressions and variable assignment..
- [PYFLOW: Python: More control flow tools](https://docs.python.org/3.12/tutorial/controlflow.html) — Branches, loops and function definitions; trace execution when a rental function is called..

### Interview question

A rental script defines a price function before reading the number of days. Which lines run immediately, and which wait until the function is called?

**A strong answer addresses:** Distinguishes a function definition from a call and follows the executed branch; Tracks variable values and types through a small hand-worked example; Compares a prediction with the actual output and names the input assumptions.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Write a small rental-desk price script using named values, one function and a branch for a multi-day discount. Predict its output before running synthetic one-day and multi-day bookings.

**Acceptance criteria:**

- Label the bookings synthetic and record the Python version and run command.
- Show the executed lines, intermediate values and predicted versus observed totals for both bookings.
- Explain why changing a numeric day count to text fails or changes behavior; do not silently substitute an answer.
- State that the chosen prices and discount are teaching fixtures, not a business pricing policy.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** Local Python 3.12 target and synthetic rental fixtures; no live provider or browser Python. Hour ranges are planning estimates, not learner-calibrated measurements.

**Study estimate:** 1–2 hours guided study + 2–3 hours exercise. These are uncalibrated learner-effort estimates, not measured timings or an implementation schedule.

### Primary readings

- [PYDATA: Python: Data structures](https://docs.python.org/3.12/tutorial/datastructures.html) — Lists, tuples, dictionaries and comprehensions for small rental records..

### Interview question

The desk reads days as "3" from CSV and as 3 from JSON. Why can the same rental total calculation behave differently, and how would you inspect the record?

**A strong answer addresses:** Distinguishes text from numeric values instead of assuming a file format validates fields; Uses a dictionary or named attributes to explain field meaning and a list to hold multiple records; Checks counts and values after a file round-trip and explains a malformed or missing field.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

**Acceptance criteria:**

- Record the synthetic fixture, file encoding, Python version and reproduction command.
- Check the three-ticket count, field names and converted day counts after each round-trip.
- Compare a tuple position with a named field and explain why the chosen representation helps this desk.
- Show an invalid numeric field and the observed failure without dropping the row silently.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

## M02-L10 — Read errors and prove behaviour

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M02-L09](M02.md#m02-l09)

**Learning outcome:** Diagnose a failed rental calculation from its traceback and write tests that distinguish valid input from an explicit rejection.

**Topics:** exceptions; reading tracebacks bottom-up; raising with a message; a first unittest; what a test does not prove.

**Study estimate:** 1–2 hours guided study + 2–3 hours exercise. These are uncalibrated learner-effort estimates, not measured timings or an implementation schedule.

### Primary readings

- [PYERRORS: Python: Errors and exceptions](https://docs.python.org/3.12/tutorial/errors.html) — Read exceptions and raise a useful message rather than silently accepting invalid rental input..
- [PYTRACE: Python: traceback — Print or retrieve a stack traceback](https://docs.python.org/3.12/library/traceback.html) — Traceback frames, exception types and messages; diagnose the failing call without suppressing evidence..
- [PYUNIT: Python: unittest — Unit testing framework](https://docs.python.org/3.12/library/unittest.html) — A first TestCase, equality checks and expected exceptions for rental fixtures..

### Interview question

A rental total test passes for two days, but a caller supplies zero days. How would you use the traceback and a new test to make the failure understandable?

**A strong answer addresses:** Reads the exception type and message before following frames back to the failing call; Raises an explicit error with a useful message for invalid input; Tests a valid result and a rejection while stating that these examples do not prove correctness for every input.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Extend the synthetic rental calculation with a positive-day guard and a first unittest TestCase. Diagnose an injected wrong-type failure from the final traceback line back to its calling frame.

**Acceptance criteria:**

- Keep the failing input and annotate the exception message and relevant traceback frames.
- Run a valid-total test and an expected-error test, checking the rejection message.
- Demonstrate a deliberately broken guard causing a test failure, then restore the guard and rerun.
- Record the Python version, test command and results; list one untested boundary and avoid claiming exhaustive correctness.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** Local Python 3.12 target and synthetic rental fixtures; no live provider or browser Python. Hour ranges are planning estimates, not learner-calibrated measurements.

## M02-L11 — Set up environments, scripts and notebooks

**Delivery:** planned · full lesson contract: not_met · interaction: none · artifact: none

**Prerequisites:** [M02-L10](M02.md#m02-l10)

**Learning outcome:** Reproduce a small rental summary in a fresh environment, move its notebook logic into a script and commit the intended file change.

**Topics:** virtual environments; pinned packages; running scripts versus notebooks; notebook-to-script conversion; Git basics for one file.

**Study estimate:** 1–2 hours guided study + 2–3 hours exercise. These are uncalibrated learner-effort estimates, not measured timings or an implementation schedule.

### Primary readings

- [PYMODULES: Python: Modules](https://docs.python.org/3.12/tutorial/modules.html) — Imports, the main module and running a file as a script..
- [PYVENV: Python: venv — Creation of virtual environments](https://docs.python.org/3.12/library/venv.html) — Create an isolated environment and record installed package versions for reproduction..
- [JUPYTER: Jupyter: The Jupyter Notebook](https://jupyter-notebook.readthedocs.io/en/v7.4.5/notebook.html) — Notebook cells, execution state and export; compare a fresh top-to-bottom run with a rental-summary script..
- [GITBASICS: Git: Recording changes to the repository](https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository) — Inspect, stage and commit one rental script; distinguish working-tree edits from the staged snapshot..

### Interview question

The desk notebook shows the right total only after cells were run out of order. What would you record and change before another person runs the rental summary?

**A strong answer addresses:** Restarts the kernel and runs cells in order to expose hidden state; Records the interpreter, pinned package versions, fixture and fresh-environment commands; Moves the calculation into a script with explicit inputs and inspects the Git diff and staged file before committing.

Score 0–3 using the [shared interview rubric](../README.md#interview-rubric).

### Production exercise

Create a local virtual environment for a synthetic rental-summary notebook, record exact installed package versions, and move the calculation into a script. Reproduce the same total from a fresh kernel and a new environment, then use Git to commit only the intended script change.

**Acceptance criteria:**

- Record the actual Python and notebook/kernel versions, pinned requirements and environment creation/run commands; exclude the environment directory and secrets from Git.
- Use the same labelled synthetic rental fixture and compare fresh notebook and script outputs with a hand-computed total.
- Show how running a dependent cell first fails, then remove reliance on hidden cell state in the script.
- Show status, diff and staged diff for the one-file commit, and explain what the snapshot does not include.
- State that local reproduction does not prove compatibility with every operating system or package release.

**Evidence to submit:**

- Versioned artifact or design specification.
- Baseline or hand-checkable fixture.
- Results or expected-results table including a failure case.
- Decision and limitations note.

**Resources:** Local Python 3.12 target and synthetic rental fixtures; no live provider or browser Python. Hour ranges are planning estimates, not learner-calibrated measurements.
